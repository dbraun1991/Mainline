# ADR-0010: Ids — RFC 4122 UUIDs via `crypto.randomUUID()`, kept prefixed

- Status: Accepted
- Date: 2026-09-09
- Relates to: [ADR-0003](0003-data-model.md)

## Context

ADR-0003 established that every storyline and event carries its own
generated id (so a rename never breaks the `storylineId` reference) but
never pinned down the id's actual format. `js/utils.js`'s `uid(prefix)`
generated a short `Math.random().toString(36)` string — random enough for
this app's actual collision risk (a solo author's own plots, at most
hundreds of storylines/events), but not a real UUID, and not something to
lean on if project files ever get merged, shared, or generated externally
— by hand, by a script, or by an LLM following
[the import DSL](0011-llm-import-dsl.md) — where two independently
generated short random strings colliding is a real (if still small) risk
a full UUID's keyspace makes negligible.

## Decision

`uid(prefix)` now returns `` `${prefix}-${crypto.randomUUID()}` `` — a
real RFC 4122 v4 UUID, generated via the browser's native `crypto` API
(no dependency needed, and a secure-context-only API, which both `npm run
dev` on `localhost` and the deployed GitHub Pages `https://` site already
are). The existing type prefix (`sl-`, `ev-`, `plot-`) stays in front of
it — still a real UUID, just easier to eyeball which type an id refers to
mid-debugging than a bare one would be.

## Consequences

**Positive**

- Real, standard id format — safe for ids to be generated by more than
  one source (this app, a hand-edited JSON file, an LLM following
  `docs/llm-import-dsl.md`) without a meaningful collision risk, unlike
  the previous short random strings.
- No new dependency — `crypto.randomUUID()` is a native browser API.
- The type prefix means an id like `sl-3f2a1c4e-...` is still legible at a
  glance as "a storyline," unlike a bare UUID.

**Negative / risks**

- Ids are longer (roughly 3 + 36 characters vs. the previous ~10) — a
  cosmetic cost only; nothing in the app displays ids to an end user, and
  `public/data/example.json`'s short hand-authored ids (`sl-main`, `ev-1`)
  are untouched, static example content, not something the app
  regenerates on load.
- `crypto.randomUUID()` needs a secure context (`https:` or `localhost`).
  Not a real constraint here — both dev and the deployed site already meet
  it — but worth knowing if this code is ever reused somewhere that
  doesn't.

## Alternatives considered

- **Bare UUIDs, no type prefix.** Rejected: strictly "more correct" to the
  letter of "ids have to be UUIDs," but loses the at-a-glance readability
  the prefix gives while debugging, for no practical benefit — nothing
  parses or validates the prefix as part of the UUID itself.
- **A UUID-generation library** (e.g. `uuid` on npm). Rejected: the native
  `crypto.randomUUID()` API already does exactly this, with no dependency
  to add or keep updated.
